# PLUS POINT — source-of-truth architecture

Updated 2026-10-21. Local development scope; production acceptance is separate. Actual test evidence is in VERIFICATION_STATUS.md. The original blueprint is preserved under docs/archive. RESEARCH_ALIGNMENT.md maps the owner's October 17 research handoff to the implementation and remaining gaps.

## Shared record choices and form controls

`choices.page` delegates to native `search_widget` and `build_for_autosuggest`, retaining the caller's filters, custom query, reference field and permission checks. It uses bounded request pages and continues until an empty page, including queries with smaller internal limits. The client cancels stale results, deduplicates IDs, sorts displayed titles A–Z and removes the autocomplete display cap. Disabled Currency metadata is included because existing company/client save paths enable chosen currencies; inactive workers/items and other native business filters remain in force. Native forms, dialogs and grid controls use the shared enhancer. Event timeline selectors return all matching plans; inventory availability no longer limits its item lookup to 500.

`forms.js` uses input modes, before-input/paste guards, format guidance and native-form validation. Names support Unicode letters/marks and normal name punctuation; phones and identifiers retain their useful separators. Business names, addresses and free text are not subjected to person-name restrictions. `input_rules.validate_document` validates supported native/PP records and their numeric child fields, preserving unchanged legacy personal values. Worker import preview shares the same rules. Native email/date, business bounds, financial approval and permission validation remain authoritative.

`form_defaults.context` returns only permission-readable saved project/company data. Sites and agreements auto-select only when unique; rates come only from an existing event plan. The client checks the current field against its pre-request snapshot before filling it, and explicit edits remain possible. New event forms reuse the active client context; onboarding can explicitly copy its saved address into the venue.

`record_actions` restricts removal to supported customer-side records and native delete permissions, locks selected records, checks posted/approved state and delegates to `frappe.delete_doc` without force or ignored links. Native System Manager draft-delete permissions are enabled for work entries, daily registers and milestones. Approved work/milestone controllers and native submitted/link checks still protect history. Batches of up to 50 use a savepoint, including rollback of native contact/address cleanup if a client is linked. Client confirmations disclose removal of unshared contact/address profiles. These actions are not a financial reversal or an approved-attendance correction workflow.

## Scope and non-goals

Customer setup uses native FieldGroup controls on Desk Page `pp-onboarding`, with company-owned `Company.pp_event_setup_state`. PP Workspace Settings binds one subscribed business profile and stores pre-company skip progress. A sticky skip action unlocks other tools and retains saved progress; sidebar entry resumes it. Native visibility and conditional-required rules are applied to the inline fields. Company/user locks serialize saved steps. `workspace.py` blocks extra Company insertion, scopes Company permissions/list results to the binding and preserves older spare profiles without merging/deletion. The dashboard has one business context. Native client creation now saves Customer/Contact/Address together; existing-client selections load full contact/address details and support edits in place without nested creation. Completed onboarding steps use a server-validated high-water mark and can be revisited directly. Country currency comes from installed Frappe metadata; unused posting accounts change with an unposted business, while agreements/stock/ledger lock the base currency but allow business-country corrections. Structured venue fields and bounded finite coordinates persist on PP Site. Leaflet/OSM provides an optional, attributed map pin with a manual fallback; no external geocoder or GPS access is added. Purpose-specific vehicle fields normalize unused capacities to zero. Zero-value inventory is explicit and uses the native allow-zero valuation flag. Normal permissions, posting and reservation checks remain authoritative. Earlier setup_flow APIs stay for compatibility.

`events.py` and PP Event Plan/Staffing model inclusive venue phases and daily requirements. Crew allocation is deterministic whole-phase availability matching with worker locks, shortage refusal and transactional generated PP Assignments. Plans do not create approved work. Used attendance prevents generated-assignment release; allocated plans freeze their dates/rates/staffing. Calendars compare required/assigned heads and approved worker-days only within the exact event dates.

Native Vehicle custom fields plus PP Vehicle Booking enforce company, dates, crew seats or cargo load, exclusivity and booked capacity. There is no item manifest. PP Equipment Booking uses native Item/Warehouse/Bin quantities and a sweep-line peak of overlapping reservations, serialized on Bin locks. Reservations do not move stock. Count submissions and outgoing Stock Entry submissions protect future reservations; other native movement/cancellation paths still require production acceptance. `event_imports.py` extends the existing bounded template/preview/apply flow for catalogs, venues, vehicles, native counted Stock Reconciliation and simple event plans. First stock uses native Opening Stock/account rules, subsequent counts use native reconciliation rules.

`imports.py` supports bounded UTF-8 CSV and single-sheet XLSX snapshots, with schema-specific templates and reference-ID downloads. Parsing rejects formulas and oversized files/workbooks. A read-only row preview is cached for 20 minutes under a random token bound to its authenticated user, company and import type. Applying a preview rechecks permissions, data, ordered project locks and native posting rules inside one transaction. An internal immutable PP Import Record stores the company/type/source-ID hash and saved record reference. Company serialization plus its deterministic primary key prevents concurrent import replay. Repeated financial rows skip; changed posted rows reject; employees use explicit IDs and a restricted profile field set. Standard target document permissions, budget/tenancy hooks and GL submission are preserved. No bank API or external Sheets OAuth is introduced. Reviewed stock counts are explicit native quantity/book-value adjustments; historical finance templates retain source references. Cross-type concurrency stress and production role/privacy acceptance remain separate release work.

PLUS POINT supports event organizers and their crew operations: client contracts, projects/sites, worker allocations, contractor attendance/dehadi, daily and fixed price billing, wages paid and operational profitability. High4Tech operates SaaS accounts. Reuse ERPNext/HRMS rather than rebuilding an ERP, payroll, authentication server, REST framework or payment gateway. Native mobile apps, biometrics and statutory payroll customization are outside this increment.

## Database relationships and validation

Tenant site/database -> native Customers/Contracts/Projects/Employees. Project links Company and Customer. PP Contract Terms links one Contract/Project pair. PP Site belongs to Project with optional same-project parent. PP Assignment links Employee, site/project/terms, dates and rates. PP Work Entry snapshots those references and rates. Submitted registers create approved work entries in one transaction. PP Milestone links fixed terms. Native Sales Invoice Item custom fields reference work/milestone sources. PP Wage Settlement links Employee, Project and a unique submitted native Payment Entry.

Historical rate snapshots are immutable; used assignment identities/rates/start dates and economic contract terms cannot be rewritten. A used assignment may close earlier only if all saved work remains within its dates; it cannot reopen or extend. Same-worker/same-site assignments cannot overlap (inclusive dates). Assignment then employee locks follow work insertion's order; the employee lock serializes overlap checks under the tested READ COMMITTED deployment. Different-site assignments can overlap for split days; work-entry validation enforces the aggregate day cap. Employee row locks also serialize settlement limits; terms locks serialize milestone caps and invoice reservations. No commits inside posting hooks. Queries used for totals disable default pagination. Native Version records retain changes. Production requires realistic large-volume profiling and audited attendance correction/reversal workflows.

## Daily wage and contract billing rules

Both required models are explicit: per worker-day billing and fixed price milestone billing.

Daily: earned wage = agreed snapshot wage rate × attendance units; client earned revenue = client rate × units. Units are 0, 0.5 or 1. Each employee may total at most one worker-day across sites on a date; employee/site/date cannot duplicate. Fixed: daily wages remain independent; worker-day client revenue is zero. Approved milestones recognize revenue; their combined value cannot exceed fixed contract value. Decimal arithmetic uses two currency decimals and half-up rounding. Custom terms and settlements use company currency only.

Always distinguish contract value, earned revenue, invoiced net/gross, receivable balances settled, outstanding balances, wages earned/paid/outstanding, other costs and operational profit. Settled invoices may include credit notes/write-offs; they are not automatically cash collected. Other costs use native Project purchase/expense-claim totals, excluding taxes, overhead and unallocated costs. Do not book the same contractor wage again as a project purchase/expense. Reports are operational contribution, not statutory net profit.

Invoice creation creates a native Draft for review and reserves sources. Draft deletion/cancellation releases them; submission marks milestones Invoiced. Duplicate sources, incorrect customer/project/company, source removal and amounts differing from the approved value converted at the invoice rate are rejected. Native credit notes exist; partial source credits/rebilling need a dedicated adjustment workflow before commercial release. Wage settlements allocate full submitted employee Payment Entries and cannot exceed approved unpaid earnings. Native employee advances remain distinct. Operational earnings do not create payroll accrual journals automatically.

Both require System Manager and normal document permissions, reject control-plane execution, and keep one company/currency per report. Tenant custom lists show familiar labels and omit the internal name column/filter, while backend names and references remain intact. The native sidebar still filters entries by document permissions. Platform navigation is excluded from these tenant changes. USER_GUIDE.md describes the workflow; UX_DESIGN.md records the design reasoning and limits.

The boot extension sets native `on_apps_screen=False` on engine app entries, leaving their route/dock metadata intact. Customer sites show one PLUS POINT product entry; the control-plane site shows one High4Tech admin entry. This is presentation, not access control. Shared HR/account/user tools remain native and are linked within the customer workspace, subject to existing permissions. ## Tenant isolation and permissions

Native Frappe site per tenant with distinct MariaDB database/user. Validated Host selects the site; browser tenant IDs never select another database. The separate platform.localhost site requires pp_control_plane=true and High4Tech Platform Admin for registry mutations. A role on a tenant site grants no platform access or automatic cross-site support login. Development Administrator is a bootstrap identity; production needs named users and MFA.

## Subscription lifecycle

Reuse ERPNext subscriptions/plans, invoices and manual Payment Entry confirmation. PP Tenant records organization/contact, subscription, suspension and active-user/worker/site limits. A trusted same-host operator worker runs outside HTTP, creates native sites and installs pinned apps. Every 60 seconds it synchronizes Active/Trialing/Grace Period eligibility and explicit period expiry to protected tenant site_config. Expired/suspended/unpaid/cancelled sites reject document writes while retaining read-only access. Limits include reactivation and use row locks. No configured entitlement means uncontrolled Development mode; all commercial tenants must use provisioning. Missing expiry on a configured entitlement fails closed.

Tenant web users cannot edit site_config. Hooks cover standard insert/save/submit/cancel/delete and allow audit/auth infrastructure records. Audit privileged upstream methods that write SQL directly before commercial release; hooks are not proof of universal enforcement. Same-host configuration avoids premature remote signing infrastructure; multi-host deployment needs authenticated agents and signed short-lived entitlements. Suspension propagation takes up to one worker interval. The worker never deletes sites. Production needs observable job state, unique onboarding credentials and recovery tooling.

Controlled development billing uses native manual workflows with no external money movement. Production must use an ERPNext-supported Payment Gateway Account adapter, verified webhooks and idempotency; never build a card processor.

## Local deployment and security

Windows Docker Desktop Linux engine; loopback web/socket ports; private database/Redis network; persistent named bench/database volumes; editable app bind mount. Ubuntu integration is unnecessary. Fresh local secrets are generated into ignored .env and never printed/committed. Do not expose developer containers or reuse local credentials commercially. Back up using native bench backup --with-files and copy backups to private off-host storage. Volumes are not backups; backups/site configs never enter Git.

## Production direction and cost

Build an immutable custom image with the pinned official frappe_docker layered build. Shared web/workers/scheduler/socket/frontend services with many isolated sites can start on one appropriately sized Linux host; separate servers per tenant are unnecessary. Add TLS, protected admin network, monitored queues/errors/disk, persistent MariaDB/sites, private Redis, encrypted offsite backups, retention and tested restores. Size capacity from measured workload. Production manifests, restore drills, monitoring and independent security review remain incomplete. Never deploy the disposable pwd.yml demo or this developer image commercially.

Architecture choices favor maintained upstream software and a small extension surface.

## Transaction isolation refinement

The pinned MariaDB 11.8 image enables InnoDB snapshot isolation. Simultaneous worker-day writes exposed error 1020 under REPEATABLE READ. compose.yaml therefore explicitly selects READ COMMITTED, and financial duplicate/cap checks use current locking reads with employee/contract serialization. This setting is part of the tested deployment contract; preserve it in production. Ten simultaneous draft attendance requests produced one creation and nine validation rejections, with all temporary drafts deleted. Larger mixed-workload/deadlock testing remains required. Native site encryption keys are initialized before web startup to avoid stale configuration during first API-key generation.

Reference: https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables#innodb_snapshot_isolation .

## Operational spending control and state feedback

The owner clarified that a separate spending budget is required, rather than a client billing limit. Reuse native Project.estimated_costing, labelled Spending budget on customer sites, with an explicit native Custom Field pp_enforce_spending_budget. It starts disabled; System Manager controls budget/stop changes through native Project saves and their history. Fixed client values and approved milestone caps remain unchanged.

plus_point.budget sums approved PP Work Entry wages, submitted Purchase Invoice Item base_net_amount and approved/submitted Expense Claim Detail base_sanctioned_amount, using row project or parent fallback. Rejected/cancelled claims and draft/cancelled invoices are excluded; tax, overhead, timesheet, stock and unallocated costs are outside this operational measure. Existing project_summary now reads these posted expense sources directly so report spending is not dependent on cached Project update frequency. No worker payment is counted a second time.

Project row locks serialize cost increases. New draft-work snapshots lock Project before Assignment/Employee; approval and whole-register checks take that same project lock before comparing totals. Purchase/claim submission and allowed post-submit updates lock affected projects in sorted order and exclude their existing contributions before evaluating replacement costs. The register checks its whole proposed amount before creating work entries. Server validation rejects increases above the enabled limit, even through REST; cost reductions and zero-cost records remain allowed during an existing overrun. Changing a budget below existing costs retains those costs and shows an overrun rather than rewriting history.

The read-only, manager-only budget preview validates the supported document type and project/document permissions. Native client before-submit/approval events stop over-budget actions and require explicit acknowledgement between 80% and 100%. Preview is guidance; it does not authorize or bypass server validation. Native accounting budgets and other upstream validations remain in place. Form results and dashboard conditions each include a next action, with text and colour for warning/error/success/empty states. Error retry does not remove normal work tools.

## Current-rate overview currency

`dashboard.overview(company, display_currency=None)` performs the existing permission/company checks and computes all financial data and notification fingerprints in company currency first. `exchange.present` deep-copies that result and projects only known money fields using one Decimal cross rate and existing money rounding. Counts, calendar units, dates, budget levels/percentages and notification IDs remain unchanged. Source-amount signs keep unpaid/loss warnings intact when a small foreign amount rounds to zero. The original amount/currency records and all write/approval paths are untouched. Native section hubs and records continue to use company currency.

The fixed HTTPS endpoint `open.er-api.com/v6/latest/USD` supplies public daily indicative rates without an API key. Requests send no tenant data, disallow redirects and have bounded connect/read timeouts. A Redis lock and one-hour shared cache cover only public quotes. Responses must have the expected USD base, positive finite rates and an update timestamp within 48 hours; future timestamps are rejected. Unavailable rates return the unchanged base-currency overview with retry metadata. The UI displays source attribution and the actual rate publication timestamp. Raw rate tables are not exposed as an app endpoint. This is not historical FX revaluation or a bank quote.

Country suggestions and manual overrides persist in `Company.pp_invoice_currency` and native `Customer.default_currency`. Existing agreements/stock/transactions preserve `Company.default_currency`; unused company posting accounts can change with the selected base. Invoice defaults prefer the client, then company invoice preference, then accounting base. Permission-checked `billing.quote` reuses the validated public snapshot and returns base currency per invoice unit, with manual agreed-rate fallback. Approved PP source values stay in base currency; native Sales Invoice items divide them by the chosen conversion rate. Currency-specific native Receivable accounts are created/reused without relabeling existing ledgers. Native GL/payment posting remains authoritative; balances and allocated customer receipts are reported in base currency. This supports basic foreign-currency invoice/receipt flows, not a custom FX gain/loss or revaluation engine.

Crew selection is shared through public/js/crew.js and crew.py. Company-owned onboarding stores employees in its saved state; PP Event Plan.selected_crew stores the ordered explicit pool as validated JSON. Legacy unselected plans retain API compatibility. New UI flows use the explicit pool, and event staffing requirements remain separate from pool size. Native PP Assignment rows still own deployments. Available-worker reads exclude inclusive date overlaps and invalid employment dates; allocation locks employee records and uses current locking reads before posting. Bulk manual allocations share the guard and roll back as a unit. No staff login, attendance, earnings or accounting entry is generated by selection/allocation.
